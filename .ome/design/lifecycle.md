# 阶段化生命周期：问询 至 任务 至 交付 至 迭代

> 状态：设计草案 ， 2026-11-07 ， 上位：[.ome/DESIGN.md](../DESIGN.md)、[projects.md](projects.md)、[ADR-0008](../../docs/adr/ADR-0008-lifecycle-and-paradigms.md)
> 一句话：先用问询把“创意”讲清楚，再用任务阶段把事做完，最后交付并进入维护；迭代时从旧项目继承，速度更快。

## 0. 为什么需要三个阶段

现在只有一个“执行阶段”的问题：用户还没讲清楚要什么，智能体就开始拆任务，结果 spec 与创意偏离，返工都发生在最贵的地方。阶段化把不确定性前置：

| 阶段 | 回答的问题 | 失败成本 |
|---|---|---|
| 问询 | 你到底要什么、什么不做、怎么算好 | 低（改文字） |
| 任务 | 怎么做、谁做、做到哪了 | 中（改任务/重跑） |
| 交付 | 能不能用、怎么维护、怎么回滚 | 高（改产物/重做） |
| 迭代 | 上一版哪里不够、这次改什么 | 低（有基线） |

## 1. 阶段与项目状态

| 阶段 | 项目状态 | 主交互 | 产出 |
|---|---|---|---|
| 问询 | draft 至 intake 至 planning | 对话澄清 + 结构化 Brief/Spec | Brief、Spec、排除清单、验收判据、计划摘要 |
| 任务 | active（含 paused/blocked） | 图谱/看板 + 收件箱 + 按需对话 | 任务、产物、证据、验证记录 |
| 交付 | verifying 至 delivered | 验收 + 交付说明 | 产物包、来源清单、维护计划、回滚点 |
| 迭代 | iterating 至 active | 差异确认 + 增量执行 | 新版本、变更记录、对比 |

问询与任务不是两个产品，而是同一个项目的前后阶段；交付后进入维护态，随时可迭代。

## 2. 问询阶段（Discovery / Spec）

目标：让 spec 接近用户的创意，而不是接近模型的默认模板。

**智能体行为**
1. 先复述目标（一句话）+ 列出 3 个可能的误解点，请用户确认或纠正；
2. 每轮最多 3 个“会改变计划”的问题（交付形态/成功判据/约束/参考/非目标），可从上下文推断的不问；
3. 用户说“你决定”至 按默认假设推进，并在 Brief 标注“假设”；
4. 生成 Brief（目标/非目标/成功判据/约束/风险/参考）与 Spec（场景/需求/验收条件/排除）；
5. 给出“创意检查”：参考物、风格/语气、边界（必须/禁止）、可接受的取舍。

**用户可做的操作**：修改/删除任意需求、补充参考、标记“这条要保留”、切换“快速模式（少问）”/“深挖模式（多问）”。

**退出判据（门禁）**：
- 目标一句话可复述；
- 至少 1 条客观验收判据（或明确“仅人工验收”）；
- 非目标/排除清单非空；
- 用户确认 Brief（一次确认，后续修改走变更控制）。

**产物**：Brief、Spec、排除清单、验收判据、计划摘要（任务图 + 预计时长）。

## 3. 任务阶段（Build）

目标：把计划执行成可验收的产物；这是主交互阶段。

**用户看到**：图谱（依赖/并行/阻塞）、看板（进度/产物/执行者）、收件箱（审批/阻塞/待验收/超时）、节点详情（结果/判据/产物/证据/记录）。

**用户可做的操作**
| 操作 | 行为 | 记录 |
|---|---|---|
| 删除任务 | 取消任务及下游依赖；已产物保留并标注 | `task.cancelled` + 影响评估 |
| 改进任务 | 修改目标/判据后重跑；旧 Run 保留 | `task.revised` |
| 插入功能 | 新增任务并入 DAG；重算关键路径 | `task.created` |
| 暂停/继续 | 暂停项目或单任务；保留 checkpoint | `project.paused` / `task.paused` |
| 改派 | 换角色/换模型重试 | `task.assigned` |
| 接管 | 用户直接改产物或给指令 | `human.message` + 审计 |

**变更控制**：范围/验收判据变化必须先算影响（新增任务数、关键路径变化、预计时长、是否触发重新确认），再决定是否执行；不允许静默改判据。

**退出判据**：所有任务 done 或显式放弃；产物带证据；无未处理阻塞。

## 4. 交付阶段（Deliver / Maintain）

目标：确认可用、可维护、可回滚。

- 验收：按判据逐条核对（L0 脚本/L1 评审/L2 人工），产出验收记录；
- 交付物：代码/文档/截图/部署/版本号**同一次构建产出**（oh-my-software-engineering 的五者一致）；
- 维护：维护计划（回归命令、依赖升级、已知问题）、回滚点、导出包；
- 交接：冷启动测试（新会话 30 分钟内说出下一步）。

**退出判据**：验收通过 + 交付五件套齐全 + 回滚演练过（或标注不适用）+ 导出可用。

## 5. 迭代阶段（Iterate）

目标：基于已有项目快速再启动，而不是从零。

- **继承**：Brief、Spec、记忆（L4 画像/决策/约束）、产物、任务图基线；
- **差异**：只确认“这次改什么/不改什么”，生成差异计划；
- **加速**：已完成任务不重跑；只跑差异任务与受影响的下游；
- **版本**：新版本产物，旧版本保留；变更记录可追溯。

**退出判据**：差异任务完成 + 回归通过 + 新版本交付。

## 6. 与 oh-my-software-engineering 的对应

| 本设计阶段 | 技能过程域/节奏 |
|---|---|
| 问询 | P0（核实/规格化/锁范围）、P1（基线与契约） |
| 任务 | P2（原型与闭环）、P3（小步迭代） |
| 交付 | P4（审查纠偏）、P5（交付与交接） |
| 迭代 | P5 + 运维与演进（变更控制/回归/技术债） |

工程约束直接采用该技能：验证器优先分配、写操作单线程、写域隔离、任务卡 11 字段、证据落 `.ome/evidence/`、门禁=命令+输出。

## 7. 验收判据

| # | 判据 | 标准 |
|---|---|---|
| L1 | 问询门禁 | Brief 确认 + ≥1 客观判据 + 排除清单非空 |
| L2 | 任务变更可追溯 | 删除/改进/插入均有事件与影响评估 |
| L3 | 交付一致 | 五件套同一次构建；冷启动测试通过 |
| L4 | 迭代加速 | 继承率 ≥60%（不重跑的任务占比）；回归通过 |
| L5 | 用户打扰 | 正常任务阶段无强制弹窗；打扰只来自收件箱 |
